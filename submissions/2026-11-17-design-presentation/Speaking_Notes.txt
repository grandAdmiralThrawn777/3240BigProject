SLIDE 1 - Secure Embedded Water Tank Controller

I am building a C controller for one simulated water tank. The main question is whether it can make the right valve decisions while rejecting invalid or unauthorized settings changes. I will explain the design, show what the existing tests establish, and identify the parts I still need to implement. This presentation describes the design as of November 10. It does not claim that the complete tank simulation or authentication is already working.

SLIDE 2 - Project scope

I kept the scope small so the control behavior and security checks are manageable. The tank is simulated, so I do not need a physical board or plumbing. I originally proposed Rust, but switched to C because the course requires C or C++. Renode still supplies the emulated processor and peripherals. The serial interface is enough for this project, so I am not adding networking or a dashboard. Source: comprehensive design, project scope; https://renode.readthedocs.io/en/latest/introduction/testing.html

SLIDE 3 - Valve decisions

The controller uses hysteresis. Two thresholds give the valve a clear operating range instead of making it switch around one target. The exact endpoints matter: at 30 or 70 percent, the previous state stays in place. The tests check both an initially open and initially closed valve. When valid sensor input returns after a fault, the usual rule resumes. If the reading is between the thresholds, the valve remains closed because the fault closed it. Source: Source/src/controller.c and file-driven control tests.

SLIDE 4 - The planned control loop

The control step runs before command processing. I plan to treat a sample as stale when it is more than 300 milliseconds old. The current firmware has one fixed reading, so the timer and changing sensor interface are still work to complete. For the first integration I will use a documented record in emulated RAM to inject the level and timestamp. That tests the control loop, but does not establish ADC or electrical behavior. The host tank model will use the measured valve output to calculate the next volume. Sources: comprehensive design; ST RM0090 reference manual.

SLIDE 5 - Planned command checks

The planned command carries a low threshold, a high threshold, and an authentication tag. I will use an established library such as Mbed TLS and check published HMAC test vectors before using it in the firmware. A valid tag is not enough: reversed thresholds or a value above the allowed range must still be rejected. Both settings are installed together. Authentication is not implemented yet. An earlier valid command can still be replayed because this design has no nonce or counter. Sources: https://github.com/Mbed-TLS/mbedtls and https://www.rfc-editor.org/rfc/rfc4231.html

SLIDE 6 - Keeping control running

C requires explicit checks around buffers and conversions. The proposed receive queue holds 256 bytes, and a command line is limited to 128 bytes before its newline. A partial line expires after 500 milliseconds. These limits are intended to keep input work from taking over the control loop. I will test a malformed stream of 1000 bytes per second and inject a sensor fault during that stream. The valve must still close at the next scheduled control step. These timing limits are targets, not measured firmware results. Sources: testing design L01; https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/

SLIDE 7 - Tests completed on Windows

These are results from the native C programs on Windows with MinGW GCC 16.1.0. The 69 cases include the original 15 and 54 added boundary cases. The sequence test checks decisions over time and recovery from faults. The 23 parser files include four accepted inputs, 18 rejected files, and one deliberately wrong expected result. The runner correctly reports that mismatch. I am not combining these different checks into a coverage percentage. They do not test the future authentication or firmware timing. Source: Evidence/Windows_Host/summary.json in the November 12 package.

SLIDE 8 - Planned system tests

The default tank model will hold 100 liters and start at 50 liters, with 2 liters per second entering through an open inlet and 1 liter per second leaving. A normal run will last 600 simulated seconds and repeat three times. I will also test a shortage and a valve forced open. Those cases distinguish an incorrect controller decision from a condition the controller cannot physically correct. These tests are specified in files, but the model and adapter still need implementation. Source: Test_Data/Planned and the November 12 testing design.

SLIDE 9 - What comes next

The host control tests and the fixed-reading firmware give me a starting point. My next step is to verify the sensor and timer path in Renode, then add the command handling and connect the model. I have a common host runner for Windows, macOS, and Linux, but the expanded tests have only run on Windows so far. I will keep unavailable tools and unfinished tests visible in the final report. The goal is a complete, repeatable evaluation, not just a successful boot message. I can take questions about the control rule, test inputs, or security limits.
