SLIDE 1 - Secure Embedded Water Tank Controller

I designed a C17 controller for one simulated water tank. I will explain the control rule, the sensor and serial interfaces, and how I test them. The implementation has progressed since the preliminary design. I will separate the design choices from the results that now verify them.

SLIDE 2 - Project scope

I kept the scope small so the control behavior and security checks are manageable. The tank is simulated, so I do not need a physical board or plumbing. I originally proposed Rust, but switched to C because the course requires C or C++. Renode still supplies the emulated processor and peripherals. The serial interface is enough for this project, so I am not adding networking or a dashboard. Source: comprehensive design, project scope; https://renode.readthedocs.io/en/latest/introduction/testing.html The native host tools support x86-64 and ARM64 on Windows, macOS and Linux. Cortex-M4 is the separate embedded ARM target. All six host CI jobs now pass.

SLIDE 3 - Valve decisions

The controller uses hysteresis. Two thresholds give the valve a clear operating range instead of making it switch around one target. The exact endpoints matter: at 30 or 70 percent, the previous state stays in place. The tests check both an initially open and initially closed valve. When valid sensor input returns after a fault, the usual rule resumes. If the reading is between the thresholds, the valve remains closed because the fault closed it. Source: Source/src/controller.c and file-driven control tests.

SLIDE 4 - The control loop

The control decision runs every 100 milliseconds. A sensor sample older than 300 milliseconds is invalid. A sequence number protects the RAM sensor record against a partial update, and the level is checked before conversion. The firmware calculates the control decision before bounded serial service, then writes the GPIO when that service returns. This differs slightly from the original immediate-GPIO pseudocode. The measured load tests kept the virtual schedule. Source: final report, firmware and ARM sensor/serial evidence.

SLIDE 5 - Command checks

The command contains two thresholds and an HMAC-SHA256 tag. Mbed TLS 3.6.7 verifies the tag. Format, conversion and range checks still apply, and both settings change together only after the complete command passes. The next control tick uses the new settings. Replay is accepted because the design has no nonce or counter, and HMAC does not encrypt traffic. Five HMAC checks and invalid-command cases passed. Sources: final report; Mbed TLS 3.6.7 release; RFC 4231.

SLIDE 6 - Keeping control running

The queue holds 256 bytes and the line buffer allows 128 bytes before LF. The loop processes at most 32 bytes and one completed line per tick. Oversized input is discarded through LF; a partial line expires above 500 milliseconds. The timer and IRQ handling are implemented. Three 60-second Renode load modes, including a 1000-byte-per-second malformed flood, recorded no missed deadlines. The injected sensor fault closed the GPIO on its checked tick. This establishes virtual timing, not physical timing. Source: Evidence/ARM_Sensor_Serial.

SLIDE 7 - Tests completed

The baseline also includes 23 parser files and three invocation-error checks. The runtime suite covers invalid input, age, overflow, timeout, replay and repeated authentication. I checked the actual compiler target triples in CI to establish native x86-64 and ARM64 execution. The Cortex-M4 firmware separately ran 1815 sensor/serial observations and a 600-second closed-loop model test in Renode. Sources: final report Evidence directories; GitHub Actions run 42890613662.

SLIDE 8 - System tests

The C model holds 100 litres and starts at 50, with two litres per second entering through an open inlet and one leaving under normal demand. Eighteen native runs cover changing demand, shortage, a stuck-open valve, one hour of operation, and three sampling periods. The normal native and ARM feedback runs both measured 29.9 to 70.1 percent. The full abnormal-flow and sampling matrix ran natively, while Renode tested one normal closed-loop case plus sensor and serial-load cases. Source: final report and tank evidence.
